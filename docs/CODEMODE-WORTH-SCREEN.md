# Does code mode earn its complexity? Matched screening handoff

This is an exploratory **same-candidate tools-off/tools-on** experiment, not another
four-framework or Node/Rust model race. No live contestant has been run by this
worker. Do not interpret scripted qualification calls as model efficiency results.
No defaults, production authority, UI, installed assets or credential store change.

## Frozen design

- Candidate core is identical in both modes, independently pinned from the task.
  A: ordinary native tools, code mode off; Bash, read_many and batching retained.
  B: only the neutral codemode declaration; actual pinned Node QuickJS-WASI VM,
  trusted nested native broker, direct/routed outer attempts refused.
- Both receive the same public task and original five instruction-file bytes.
  Only the declared interface treatment/routing appendix differs. Native tool
  representations (including text/base64) are shared. The existing blind adapter
  serializes broker effects and disables its ambient-host asynchronous Bash fast
  path in both modes; ordinary Bash and multi-tool/read_many batching remain
  available in A. This is not a clean shell-parallelism benchmark. Fresh task Git snapshots
  contain no original object store, gold repair, private scorer or solved history.
- Repair: realistic pure half-open interval coalescing repair, including validation,
  nonmutation and touching-boundary semantics. APIs: paginated settled-order net
  aggregation with refunds/zero/negative subtotals. Workflow: ordered conditional
  approval/hold with documents, risk, optimistic versions and decreasing credit.
  Public contracts live in `agent-benchmark-worth-fixtures.mjs`; only exportTask's
  public bytes enter the isolated networkless tool box. Mock API state stays in
  its trusted per-attempt controller closure, inaccessible through shell/files.
- Serial order: repair-a, repair-b, aggregation-b, aggregation-a, workflow-a,
  workflow-b. Exactly one attempt each; no automatic repetitions or trial retries.
  Serial operation avoids intentional pair overlap; other host/provider contention
  remains possible. This is six exploratory observations, not statistical proof.
- gpt-6.1-sol LOW. Per attempt:30 provider dispatches (including failures/summary),
  2M total reported input (cached subset),20k output (reasoning subset),10min solver,
  180s absolute provider request. Six-screen thresholds180/12M/120k/60 solver-min.
  Token thresholds are checked after responses and may overshoot once/attempt.
  Dollars/quota are unknown, not zero or hard-capped. Setup/grading/drain are extra.
  Tool limits remain the existing2CPU/2GiB/128PID/1GiB tmp, no workspace disk quota;
  Windows controller limits are not host reservations.

Primary: behavioral oracle acceptance and verified completion, not exit alone.
Keep actual VM use, outer routing condition, known guest/tool errors, protocol
fidelity/unknown effects, normal handoff, oracle acceptance and complete usage
separate. Existing strict certificates and historical unresolved delivery140 /
invocation19 are unchanged; never replay that operation.

Efficiency: all dispatches and uncached input per accepted completion, including
failed attempts. Zero completions has no finite winner. Prespecified practical
signal: >=20% fewer dispatches **or** uncached input per accepted completion, no
observed correctness/safety regression and no major output/latency/error offset.
Do not choose a winning metric afterward. Cache observations are provider counts,
not assumed cold KV. Setup, storage, verification and human help also matter.
Recommendation can be narrow/no observed benefit/inconclusive; no promotion follows.

## Executable preparation / coordinator-only live door

Use absolute paths and fresh evidence directories:

```
node scripts/agent-benchmark-worth.mjs --qualify <artifact-config.json> <fresh-proof>
# Set qualificationReceipt to that receipt in the private config.
node scripts/agent-benchmark-worth.mjs --prepare <config.json> <fresh-plan>
node scripts/test-agent-benchmark-worth-policy.mjs <plan/manifest.json> <fresh-negatives>
```

Preparation does not probe a live vault. Pins cover the candidate/build receipt,
Node, guest/prelude/driver, existing tool image, runtime/adapters, task/scorer and
instruction bytes. Qualification runs real native A/B loops through the actual
**synthetic** vault and existing blind Docker tools. Each scorer has broken,
known-good and deceptive controls; repair deception includes forged success/exit.
Repair code executes only in a fresh grading Docker box, with pure builtins in a
VM, after the solver tree/RPC writers drain. The Docker boundary, not Node vm, is
its OS isolation boundary. Scorer control failures are expected, not solver scores.
B qualification includes syntax-error recovery, known missing-read refusal and
90,000-byte multibyte output before later task work and final handoff.

Coordinator alone checks the actual human approval and private credential route,
then runs the single bounded screen (never use a synthetic checker reference):

```
node scripts/agent-benchmark-worth.mjs --run-approved <plan/manifest.json> <fresh-live-results> <manifest-sha256> <actual-human-reference.json>
node scripts/check-agent-benchmark-worth.mjs <config.json> <live-results> > <fresh-summary.json>
```

Reference fields: manifest_sha256, session_id, message_id. These are evidence
pointers, not authentication/grants. The native invocation and real human message
remain authoritative. The once-only exclusive/fsynced launch intent precedes any
trial effect; copied/consumed/unknown reservations cannot launch another screen.
No inference contestant was admitted by this worker. Coordinator publishes HTML.

Unknown usage halts its attempt without replay. Unknown tool/protocol outcome
halts the remaining screen, drains actors and preserves evidence. No failed screen
is automatically replayed. Qualification/result bundles reuse existing lifecycle,
source-bound records, lossless archives and verify-before-owned-cleanup. A failed
unsealed generation is retained for exact-owned reconciliation, not swept away.
No Pi SDK event loss/truncation policy changes; this screen does not run Pi.
Prospective VM postchecks stream selected JSONL records/hash/counts rather than
materializing archives or giant SDK strings. Existing50KiB model view and8MiB
supervisor capture limits stay unchanged.

## Equal-workload host diagnostics (separate question)

```
node scripts/codemode-equal-workload.mjs <candidate-wa> <pinned-assets> <fresh-evidence>
```

Three process pairs, alternating host lead, three rounds of six **identical JS**
cases per process: processing,20-call deterministic mock broker chain, guest error,
object/array/null/unicode serialization,90kB output and known broker rejection.
No real native task tools/model calls/host effect replay.108 cases must match
output/correctness across hosts. Guest/prelude hashes are checked against both
hosts. Rust actors have Node unavailable and copied already-installed rg; no Node
bridge/fallback in V2. Node is only the comparison controller/test tooling.

Record first guest in fresh host vs subsequent fresh guests in warm host. Node's
controller/module/JIT cache can persist across pairs; Rust's first start recompiles
in each native process. start_ms includes setup/evaluation (and Node loopback/JSON),
not pure VM CPU; admit/deliver/close and process/controller setup are separate.
Memory/CPU not measured, hence unknown. Wasmtime500M fuel has no identical Node
fuel counterpart; both use30s guest deadlines and matching guest heap/stack.
These diagnostics establish host overhead/fidelity only, never autonomous value.
Error fidelity checks known category/message markers and retained partial output,
not byte-identical host-specific stack strings. Small fixed repetition counts and
observable variance do not support a universal backend performance ranking.

Self-review and focused checks only: gate_verified:false, release_verified:false.
Preparation assistant inference is real spend; its total usage/dollars remain
unknown here and must be reported separately by the coordinator.
