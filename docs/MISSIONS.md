# Missions — the loop, the command for each step, and the measurement behind every rule

> The mechanism is `scripts/mission.sh`; this file is the knowledge behind it. Where the two disagree, the
> script is what runs. Its fixture is `bash scripts/test-mission.sh` (202 checks, a scratch repository and a
> stub `wa`; no network, no model, no node). The fixture runs in the fast path: `check mission` in
> `scripts/fast.sh`.

A mission is one delegated change carried from a brief to the fleet by one session:

    brief -> launch -> watch -> independent review -> fix round -> integrate -> land
          -> deploy canary -> fleet -> clean

On disk a mission is `$MISSIONS_DIR/<name>` (default `~/Work/missions/<name>`):

| file | what it is |
| --- | --- |
| `brief.md` | the operator's brief, as given |
| `note.md` | optional; a fix round's instructions, appended to the prompt |
| `amend.log` | every amendment's delivery attempt: `<sha> <stamp> <state> <session> <receipt> <detail>`. One line per try, so the same file passed twice is ONE amendment (step 3b) |
| `amend-run.sh` | the runner `amend` writes for a resumed turn, so its rc lands in `done` like a launch's |
| `env` | the mission's facts: `NAME BRANCH BASE BASE_SHA NODE WT TOOLCHAIN TARGET WA` - the one place |
| `prompt.md` | `brief.md` + "Where you are": worktree, node, build dir, the rules |
| `run.sh` | one static runner, generated by `stage`; `start` launches it and never rewrites it |
| `started`, `done` | UTC start, and `rc=<exit> <utc end>` - a launch that finished, or died, with its code |
| `run.lock` | the mission's lock, owned by the NODE's run: `SESSION WORKTREE NODE LAUNCHER LOCKED`, taken before the CLI asks for a session and released when the node says the run settled |
| `lease.log` | every `take`, `bind`, `cli-exit` and `release` with its reason - so a missing lock is always explained |
| `run.pid` | the CLI process of this launch. Evidence, never liveness: on 18/11 the CLI exited rc=1 while the node kept writing |
| `launch.pid` | the runner `start` launched (`$!`), written before the runner can write anything. It is what makes the cap below safe: while that process is this mission's `run.sh`, `mission_run` answers `active`, even with no `run.pid`, no presence row and no session (round 6) |
| `out.log`, `err.log` | the session's output and errors, appended across launches |
| `verify.log` | every `verify` command with its cwd and rc |
| `wt/` | the git worktree on `change/<name>`; the session's code, and where `REPORT.md` goes - the handover, which removing the worktree takes with it. The round report that survives is the repo's `docs/missions/reports/<name>.md` (this mission's: `docs/missions/reports/mission-fabric.md`), and `status` reads either |

## Stage by stage, with the command

### 1. Brief

    $EDITOR ~/Work/missions/<name>/brief.md      # the artifact, its scope, the evidence that settles it

A brief says what the artifact is and what proves it. It does not say where the worktree is: `stage` adds
that, because a session left to find its own worktree allocated one and looped (item 2 of the table).

### 2. Stage

    scripts/mission.sh stage <name> origin/main ~/Work/missions/<name>/brief.md

Writes the table above: `env`, `prompt.md`, `run.sh`, and a worktree on `change/<name>` cut from the base
commit it resolved (a `git fetch origin main` runs first, and a fetch that fails is not fatal). It refuses,
by name: a name with `/`, `..` or a space; a base that does not resolve; a branch `change/<name>` that
already exists; a worktree that already exists; a missing or empty brief; no `wa` on `PATH`; and a node that
is not the one that staged it. One branch per mission is what keeps `main` out of a second worktree - the
deploy's own preflight requires exactly one canonical main checkout.

### 3. Launch

    scripts/mission.sh start <name>

One fresh session: `wa chat --once "$(cat prompt.md)"`, detached with `setsid nohup`, running in `$M` (the
mission dir, never the repo). `run.sh` exports, before it launches anything:

    # never set WASM_AGENT_RAW_CODE: run(code=...) is the one execution path (Victor 21/11) and a
    # launcher that exports the removed switch makes every run refuse by name
    export RUSTUP_HOME="$TOOLCHAIN/rustup" CARGO_HOME="$TOOLCHAIN/cargo"
    export PATH="$TOOLCHAIN/cargo/bin:$PATH"
    export CARGO_TARGET_DIR="$TARGET"     # ~/wasm-agent/target/m-<name>, this mission's own

**`start` is ONE answer, and everything else refuses.** A launch happens when, and only when, all
three of these hold. They are checked under one lock (below), and any other answer refuses by name:

1. **no launcher is alive** - `run.pid` holds a live pid whose cwd is the mission dir: the few hundred ms
   after a launch, before the node has named the session (`alive_launcher`); and, while there is no
   `run.pid` at all, `launch.pid` must not name a live `run.sh` of this mission (`launch_alive`, round 6);
2. **no process the node records is working in the mission's directory** - `session_presence` in
   `memory.db`, with `/proc/<pid>/cwd` as the answer to *where* (`writers_check`). `/proc` reports the
   path a directory really is, so both sides of that compare are resolved with `cd ... && pwd -P` first: a
   missions tree reached through a symlink is one directory with two spellings, and a bare string compare
   called a writer in it "another directory" (round 7);
3. **the node says every session of this mission is settled** - the session list, the run lease and the
   boot lease, three reads (`mission_run`).

Every other answer - **alive, held, stale, starting, unknown, unreachable** - refuses, and prints two lines:
the state by name with the reason, and the command an operator runs to clear it:

    mission: refusing [stale]: session 4444...: the node still lists run run-of-4444 in flight, but free boot
    boot-free is gone (its lease was takeable) - the owner exited, so this row is a leftover, not a launch
    permission: ...
    mission: clear it by hand: the owner has exited, so this row is a leftover: finish that one session by
    hand (wa resume --session 4444... --once "<what is left>") or settle its row (sqlite3
    ~/.wasm-agent/memory.db "update steering_runs set state='settled' where session_id='4444...'"); then rm
    <mission>/run.lock once you have checked it

**There is no `--force`.** A state this script cannot prove free is a state a human decides, and the states a
human must decide are exactly the ones a flag would have guessed past: unknown is never free, and a leftover
is not a launch permission (rounds 3 and 4).

The launcher's pid is not the evidence and cannot be (see the provenance below): everything except the local
window is read from the node, in three reads.

| read | command | what it answers |
| --- | --- | --- |
| the session list | `wa sessions` | which sessions exist and their state (`unfinished`, `answered`, `empty`), and for an unfinished one how long ago its last message was. It decides WHICH sessions are this mission's (the title marker), not whether they are settled |
| the run lease | `wa steer <session> --status --json` | whether a run is in flight for that session, and its `run_id`. This is what settles a session: `settled`, `failed` or `cancelled`, and nothing else |
| the boot lease | `sqlite3 -readonly ~/.wasm-agent/resources/claims.sqlite "select boot from claims where key='session:<id>'"`, then `BEGIN EXCLUSIVE; ROLLBACK;` on `resources/<boot>.lease.sqlite` | whether the process that owns that boot still exists: a lock that can be taken is an owner that exited, a locked one is an owner that has not (`rust/wa-capabilities/src/resources.rs`, `lease_released`). The probe writes nothing. It separates `held` from `stale`, and it never permits a launch |
| the presence row | `sqlite3 -readonly ~/.wasm-agent/memory.db "select session_id, pid, cast(strftime('%s','now')-heartbeat_at as int) from session_presence"`, then `readlink /proc/<pid>/cwd` | which process serves each session and **which directory it works in**. The runner cds to the mission dir before it starts the CLI, so a session working for this mission has the mission dir or its worktree as its cwd - measured on avell, 18/11: session 6cdf7ddf, pid 1758185, heartbeat 0 s old, cwd `/home/victor/Work/missions/mission-fabric`, a writer no `run.lock` named. The heartbeat is REPORTED, never obeyed (round 4). A `/proc/<pid>` that exists with an unreadable cwd (another user's process, hidepid) is *cannot tell*, not a process that exited (round 5). The mission dir and its worktree are resolved with `pwd -P` before that compare, so a symlinked missions path still matches (round 7) |

How they combine, and which of them permits a launch (`mission_run`: one verdict, one reason, one clear
command):

| what the reads say | verdict | launch? |
| --- | --- | --- |
| every session of this mission has a run lease of `settled`, `failed` or `cancelled` | `released` | **yes** |
| the node answered and lists no session for this mission (nothing recorded, nothing present) | `released` | **yes** - a fresh mission's first launch, and a mission whose node rows are all settled |
| `session_presence` names a live pid whose cwd is the mission dir or its worktree | `active` | no - a live process is working here, whoever recorded it, and no age is asked. The whole table is read before the answer is given, so a writer row decides even when another row of the same read cannot be placed - in either order (round 6 named the writer; round 7 stopped the read from returning at the unplaceable row that came first) |
| `session_presence` **cannot be read** - no `memory.db`, an unreadable one, no `sqlite3`, a query that fails - or a live pid whose `/proc/<pid>/cwd` cannot be read | `unknown` | no - the presence read is one of the three reads, so a read that cannot be made is the same "cannot tell" as an unprobeable boot lease (round 5) |
| a run in flight and its boot lease is **held** | `active` | no - the owner has not exited, at any age |
| a run in flight and its boot lease can be **taken** | `stale` | no - the owner exited, so the row is a leftover: settle it by hand |
| a run in flight and the boot lease **cannot be probed** (no `sqlite3`, no store, an unreadable one) | `unknown` | no - "cannot tell" is never free |
| `wa steer` answers `none` (no run row) for a session that exists | `unknown` | no - the session is **starting** (no claim row, no lease file yet), or nothing here can show it settled |
| `wa sessions` prints nothing | `unknown` | no - and the refusal names the session the mission records |
| a `session_presence` row with no pid (or a pid that is not a number) | `unknown` | no - "no pid" is not "no writer": the process serving that session, and so where it works, cannot be told (round 6) |
| `launch.pid` names a live pid that is this mission's `run.sh`, and there is no `run.pid` yet | `active` | no - the runner `start` launched is standing: it has launched nothing yet or is about to, and it is the process the 10-minute cap used to leave unrecorded (round 6) |

Why each of those is refused instead of guessed at:

* **a live run is a writer whatever its age.** `updated_at` is the run's *start*, not its last context
  boundary: measured on avell 18/11, a live run 25 minutes in answered `state=active` with `updated_at` 1533 s
  old, and round 2's 300 s window called a live run `stale` at 969 s. Round 4 does not guess from time at
  all: the run lease decides, and the boot lease says whether the owner still exists;
* **the age window is gone.** `MISSION_ACTIVE_SECONDS` no longer exists, and neither does a heartbeat age as
  a decision: a presence row is asked one thing - is that process still there - and the age it reports is
  printed in the reason, not obeyed;
* **one session ending says nothing about the next.** Measured on avell, 18/11: the mission dir's session was
  `failed` while 6cdf7ddf was writing in that same directory, which is why the presence read is asked whether
  or not the recorded session settled;
* **a session is matched to the mission three ways.** Every `stage` writes the marker `mission <name> in <wt>`
  as the **first line of `prompt.md`**, and the node shows a session's first line as its title
  (`lua/core/memory.lua` `title_from`: furniture stripped, 60 chars, then an ellipsis) - so a session is found by
  the title the node prints, whether or not the launcher survived to record anything. The second way is the
  id in `run.lock`, then in `err.log` where the CLI prints it (`wa: session <id> ok|failed` - on stderr, which
  round 1 read from the wrong stream). The third way needs neither a title nor a log: the directory the
  session's process works in - which is how a session the harness started (no `stage`, no lock, a brief for a
  title) is still refused, and still named.

**One `start` at a time, and the check plus the launch is one step.** `flock -n` on `$M/start.flock`, held by
the `start` shell until the launch has a `run.pid` and closed then. The kernel drops it when that shell exits,
so a start that dies leaves NOTHING to clear by hand, and a second `start` refuses while the first is inside
the window (its refusal says so, and names the file). Round 3 held the same window with
`mkdir $M/start.lock` and cleared a dead holder with `rm -rf`: two starts could then both clear it and both
take it, which is why the directory is gone (round 4, item 2). Without any exclusion two starts read
"nothing running" in the same breath and both launched - measured: 10 of 10 simultaneous pairs, each writing
`run.lock` with `>`.

`start` never resumes either: there is no `--resume` in the runner, and one launch is one fresh session.
`done` is removed before the launch and written after it with the rc, and `run.pid` and `launch.pid` are
cleared by `start` before it launches (after the gate above has read them), so a stale pid file cannot make
`start` return before the new runner has taken the lock. The wait for `run.pid` is capped at 600 s
(`MISSION_START_WAIT_SECONDS`, a seam the fixture shortens): a runner that is alive and has written no
`run.pid` when the cap is reached is a refusal, and it stays named in `launch.pid` for the next `start`
(round 6: before that record existed, the next `start` found no `run.pid`, no presence row and no session
and launched a SECOND runner beside the live one).

#### Clearing a stuck mission by hand

`start` prints the command for the state it is in. What to look at, in order:

    scripts/mission.sh status <name>     # the verdict, the session, the launcher, the lease log
    scripts/mission.sh report <name>     # the same, plus failures, verify and the handover file

| state | look | clear |
| --- | --- | --- |
| `launcher` | `ps -o pid=,cmd= -p "$(cat <mission>/run.pid)"` | wait for `<mission>/done`; if that pid is not this mission's runner, `rm <mission>/run.pid` |
| `launcher`, the runner is alive and wrote no `run.pid` in 600 s (`launch.pid`) | `ps -o pid=,cmd= -p "$(cat <mission>/launch.pid)"`; `tail -5 <mission>/out.log <mission>/err.log` | nothing here kills a process: look at what it is doing and let it end. While it lives every later `start` refuses `[active]`; once it is gone the file names a dead pid and refuses nothing (round 6) |
| `launcher`, "the runner ended rc=95" | `tail -5 <mission>/err.log; tail -5 <mission>/out.log` | nothing to clear: the runner exited before it wrote `run.pid` (95 wrong node, 96 cannot cd, 97 no mission dir, 98 no env), so nothing was launched. Fix what the rc names and `start` again (round 5) |
| `active`, a writer in the directory | the refusal names the session, the pid and the cwd: `ps -o pid=,cmd= -p <pid>`, `wa steer <session> --status` | nothing here kills a process: let it exit, or kill it yourself once you know what it is. The launch is allowed when it is gone |
| `active`, a run in flight with its boot held | `wa steer <session> --status`; `sqlite3 -readonly ~/.wasm-agent/memory.db "select pid, heartbeat_at from session_presence where session_id='<session>'"` | the run ends when its process exits. If you have checked that the process is gone and the row still says `active`: `sqlite3 ~/.wasm-agent/memory.db "update steering_runs set state='settled' where session_id='<session>'"` |
| `stale`, the owner exited | the boot lease can be taken, so nothing is writing | finish that one session by hand (`wa resume --session <session> --once "<what is left>"`) or settle its row with the same `update steering_runs`, then `rm <mission>/run.lock` once you have checked it |
| `unknown`, the node cannot be asked | `wa sessions 100` and `wa status` on the node | make the node answer, then `scripts/mission.sh status <name>` once. Nothing is cleared by guessing |
| `unknown`, a session that is starting (no run row, no claim, no lease file) | `wa steer <session> --status` | wait a moment and read again: a launch is refused only while that session is not settled |
| another `start` - or a `clean` - holds the lock | its refusal names `start.flock` | nothing: the kernel releases it when that `start` (or `clean`) exits. A leftover *file* is not a lock, and is not cleared by hand either |

Two of those rows write into the node's own store (`memory.db`). They are the last resort, and they are named
because nothing in `wa` can settle a run: `wa help` has no cancel, and `steer` only queues a note into a run that
is in flight. Check the process first - a row you settle while its process is alive is a second writer with
a clean-looking record.

### 4. Watch

    scripts/mission.sh status <name>      # one mission; no name: every mission under ~/Work/missions
    scripts/mission.sh report <name>      # status + failures + verify + REPORT.md + err.log + resume line

`status` reads the files, not the transcript: commits and changed files against the recorded `BASE_SHA`
(`git rev-list --count`, `git diff --name-only`), dirty paths, `done`, and
`failures` = `grep -c '^! run_failed' out.log`, with the newest failure quoted. A real failure is a
`run_failed` line from `lua/core/run_failure.lua`; the word "failed" in prose is not one.

Its `run` line is the verdict from `mission_run` - `active`, `stale`, `released` or `unknown` - with the
reason behind it and the command that clears it, so `status` and a refused `start` say the same thing in the same
words. It is **not** derived from `run.pid`: the `launcher` line reports that pid and says in the line itself
that it is not liveness - and, before the runner has written a `run.pid`, it reports the runner recorded in
`launch.pid` instead, which is a launcher of this mission and still not liveness (round 6). Only `released` permits a launch. `status` is an observer of the node's word, so a lock
the node says is settled is released by the read that saw it, with a `release` line in `lease.log` naming
`by=status`. `verify` and `clean` keep the same rule as `start`: both refuse every verdict but `released`
(`clean` since round 5 - a leftover row and a read that could not be made both reached `git worktree remove`;
`verify` since round 7 - it runs a command in `wt/`, so `unknown` and `stale` let it run cargo beside a
possible writer). `verify` never kills a process, and `clean` takes `start.flock` before it removes anything and
keeps the file: deleting the lock a clean holds would hand the next `start` a different inode to lock (round 7).

A mission staged **before** this script (no `env` file - every mission under `~/Work/missions` on 18/11) is read
from its worktree instead: branch, commits/files/dirty against the `origin/main` merge base, and
`running: unknown (launcher before this script recorded no pid)` - because the old runner recorded no pid and
`no` would be a claim nobody made.

    wa watch <node> <session>             # a session on another node, read-only
    wa steer <session> "<note>"           # queue a note into a run that is still in flight

### 4b. Amend a worker that is already running

    scripts/mission.sh amend <name> <file|->     # a change from the planner, while the worker is running

The worker reads its brief ONCE, at start, so a change that arrives mid-turn used to wait for the whole turn
to end. Measured on launch-opening 22/11: three changes from Victor (21:33Z, 23:32Z and the v1.0 wording) each
waited for a turn and the mission took three passes, because the orchestrator had no door into the live run -
`wa chat --session <id>` on a live run is refused `resource_busy` (the session's claim belongs to the run),
and killing the process is what leaves a session claimed.

`amend` does two things and nothing else: the text is APPENDED to `brief.md` under
`## Amendment <UTC> (from the planner)`, and the same text - labelled `[amendment <UTC> from the planner]` -
is handed to the product's own steering door (the `wa steer` line above), which the run consumes at its next
context boundary, atomically with its read receipt, into its transcript as a user row.

- **The stamp is the amendment's identity.** `amend.log` keeps one line per delivery attempt, so passing the
  same file twice appends nothing and delivers nothing a second time; the second call reports what the NODE
  says became of the first: `read` (with the message it became), `queued`, or `deferred` - a run that
  settled before its boundary, which is delivered by resuming the worker instead.
- **Nothing in flight is not nothing to do.** A worker between turns, or one that finished (`done` carries
  its rc), is RESUMED with the amendment as the message of its next turn (`wa chat --resume <id> --once`), and
  that turn's rc lands in `done`. The command says which of the two happened and never calls an appended note
  delivered.
- **The session is the node's answer, not a guess.** The CLI prints `wa: session <id> ok` to stderr when its
  turn ENDS, so during a live turn neither `run.lock` nor the logs name the session. `amend` asks the node, in
  two ways: the sessions carrying the mission's title (the first line of `prompt.md`, the criterion a launch's
  gate uses), and - for a mission staged the way the factory's own launcher does it, brief first and no marker -
  the session the node records as working in the mission's directory (`session_presence` plus `/proc/<pid>/cwd`).
  Then `run.lock`, then the `wa: session` line a finished run left in the logs.
  The resume runs from a runner `amend` writes (`amend-run.sh`), in `amend`'s own environment: a resume
  spawned through `host.exec` gets a scrubbed environment, and a mission's provider settings arrive that way
  (measured: the resumed CLI answered "No provider is configured" and made no model request).
- **Appended, never inserted.** `prompt.md` is written once at `stage` and never rewritten, so the worker's
  prompt prefix - and its cache - is untouched; the brief only grows, and the check that it only grew is in the
  script. The worker is told what an amendment is in its prompt: newer than the brief where they disagree, and
  named in the report by its UTC stamp.
- **It refuses by name**: no mission, no `brief.md`, an amendment of no words, more than 32000 bytes (the
  door takes 32768 including the label), a mission with no session running or recorded, a node that cannot be
  asked, and another `start`/`clean`/`amend` holding the mission's lock. A refusal appends nothing, except
  the one case where the text is already in the brief and only the delivery failed: then `amend.log` records
  `undelivered` and the same command delivers it later, once.

Its fixture is `node scripts/test-mission-amend.mjs` (38 checks, on the fast path): a scratch repository, a
scratch node store and a real `wa chat --once` against a local SSE fixture, with the amendment sent by another
process while the first turn is held at its model request.

### 5. Verify, in the mission's own environment

    scripts/mission.sh verify <name> bash scripts/fast.sh
    scripts/mission.sh verify <name> bash scripts/test-mission.sh

Runs the command in `wt/` with codemode, the toolchain and the mission's `CARGO_TARGET_DIR`; appends
`--- verify <utc> <command> (cwd ...)`, the output and `rc=<n>` to `verify.log`; exits with the command's rc.
It refuses every verdict but `released` (round 7: `active` was its only refusal before, so an `unknown` read or a
`stale` leftover ran the command beside a possible writer), so a verify never competes with a session for the
same tree. A refusal writes nothing: no `verify.log` line, and the command is not run.

### 6. Independent review

    wa eval reviewer change/<name> --brief ~/Work/missions/<name>/brief.md
    wa eval report

A reviewer that shares nothing with the session - its own home, its own session (`docs/HARNESS-EVALUATOR.md`).
Self-review is allowed and must be labelled self-review, never independent review, and never a fabricated
receipt. A finding accepted or rejected is marked: `wa eval reviewer mark <id>#<n> accepted`.

### 7. Fix round

    $EDITOR ~/Work/missions/<name>/note.md     # what the review found, as findings, not prose
    scripts/mission.sh start <name>            # a NEW session; out.log keeps the previous one

Start with the blockers. The round is a new session on the same worktree and branch - not a resume - so
nothing inherits the previous turn's context, and a failed launch is never replayed. For a staged mission
the note is appended to the prompt the next time it is staged.

### 8. Integrate

    node scripts/landing-queue.mjs preflight --branch change/<name> --checks "bash scripts/fast.sh"
    node scripts/landing-queue.mjs land --branch change/<name> --checks "bash scripts/fast.sh"

The queue takes the merge tree in order: it refuses a dirty canonical tree nobody owns, retests only what
the move changed, and judges the result against what `main` already fails. `bash scripts/fast.sh` must pass
before you integrate, and the report says what it skipped.

### 9. Land

The same `land` step pushes and reads `origin/main` back; the branch is deleted and the canonical tree is
left clean. Never by hand in the canonical checkout. Then:

    scripts/mission.sh clean <name>            # worktree goes; branch, logs, done, verify.log stay

`clean` refuses a dirty worktree (commit it, or `clean --force` to discard), refuses any verdict but
`released` - a live launch, a leftover row, a node it cannot ask - takes `start.flock` before it removes
anything and refuses while a `start` holds it (round 7: the removal used to take the worktree a start was
launching into), removes only the worktree and the runner, prunes, and keeps the branch - its commits are the
mission's result. `start.flock` stays on disk: the lock is the kernel's, not the file's. `status` for a cleaned mission still reads `out.log`, `done` and `verify.log`.

### 10. Deploy canary, then the fleet

    wa update --all                                    # read-only: what an update would install, per node
    wa update <canary> --status                        # what the canary runs now
    wa land --ready --canary <node> --account <node>   # waves: canary alone, middle, account node last

A deploy goes canary first and alone, so a broken commit breaks one node. A node that is the channel you
would repair it through (`mail`, `openclaw`) goes last. `scripts/fleet-install.sh <artifact-url>` refuses a
binary whose maximum `GLIBC_` symbol the host does not have, before it swaps anything - that refusal is why
`mail` no longer disappears for two days.

## What the script does not do

No daemon, no watcher, no scheduler: nothing runs between your commands. It does not merge, push, deploy,
review or decide; it does not retry a launch; it does not `pkill` anything. The judgement in steps 6-10 stays
with the operator and the session, and the script's job is to make a mission's state readable without
reading a transcript.
