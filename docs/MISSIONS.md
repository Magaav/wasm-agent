# Missions — the loop, the command for each step, and the measurement behind every rule

> The mechanism is `scripts/mission.sh`; this file is the knowledge behind it. Where the two disagree, the
> script is what runs. Its fixture is `bash scripts/test-mission.sh` (52 checks, a scratch repository and a
> stub `wa`; no network, no model, no node). The fixture runs in the fast path: `check mission` in
> `scripts/fast.sh`.

A mission is one delegated change carried from a brief to the fleet by one session:

    brief -> launch -> watch -> independent review -> fix round -> integrate -> land
          -> deploy canary -> fleet -> clean

On disk a mission is `$MISSIONS_DIR/<name>` (default `~/Work/missions/<name>`):

| file | what it is |
| --- | --- |
| `brief.md` | the operator's brief, as given |
| `note.md` | optional; a fix round's instructions, appended to the prompt |
| `env` | the mission's facts: `NAME BRANCH BASE BASE_SHA NODE WT TOOLCHAIN TARGET WA` - the one place |
| `prompt.md` | `brief.md` + "Where you are": worktree, node, build dir, the rules |
| `run.sh` | one static runner, generated by `stage`; `start` launches it and never rewrites it |
| `started`, `done` | UTC start, and `rc=<exit> <utc end>` - a launch that finished, or died, with its code |
| `run.pid` | the live launch, so liveness is a pid and its cwd - never a pattern |
| `out.log`, `err.log` | the session's output and errors, appended across launches |
| `verify.log` | every `verify` command with its cwd and rc |
| `wt/` | the git worktree on `change/<name>`; the session's code, and where `REPORT.md` goes |

## The measurements

Each rule below is a mechanism in `scripts/mission.sh` because something failed without it. Cited where it
was measured; "measured on avell, 18/11" means it was reproduced while writing this file.

| failure | what was measured | where |
| --- | --- | --- |
| **toolchain missing, so the build moved to the laptop** | A mission on `work` reported "this node has no Rust toolchain - `cargo --version` answers `bash: line 1: cargo: command not found`, there is no `~/.cargo` and no `rust/target`", and delivered nothing for its three cargo items. The build moved to a 4-core laptop that has no cargo either (measured on avell, 18/11: `work` = 4 cores, `no-cargo`, load 8.15/10.47/11.86; the brief records load 27 when it happened). | `harness-fixes-rust` REPORT.md, items 6-8 |
| **CodeAct loop on `session_worktree`** | The model called `session_worktree({"action":"status"})` three rounds in a row, `guard_repeated_calls` ended the turn, `rc=1`: the session was looking for a worktree the brief never named. | `~/Work/missions/harness-fixes/out.log` |
| **wave registration refusal that named nothing** | The wave's registration answered "attempt to call a nil value (field 'wave_admission_outcome')" - a refusal no operator can act on. It refuses by name now: `wave registration unavailable: <why>`. | commit `62c3c064`, item 4; `scripts/lib/wave-guard.mjs:12` |
| **the progress guard killed a legitimate wait** | `! run_failed: guard_repeated_calls ... codemode({"code":"const r = await tools.operation({action:await, id:op-..., wait_for:settled})"` - a turn that awaited one long build was stopped as a loop after 126 rounds. A wait is one await of an operation id, never a poll. | `~/Work/missions/harness-fixes-rust/out.log` |
| **`pkill -f` / `pgrep -f` matched their own command line** | Measured on avell, 18/11: `bash -c "pkill -f <pattern>"` printed `Terminated`, exited `143`, and never ran the next line - it killed the shell that carried the pattern. `bash -c "pgrep -af <pattern>"` listed its own shell (`bash -c pgrep -af <pattern>; echo rc=$?` -> `rc=0`, one match: itself). | reproduced; see the `alive()` comment in `scripts/mission.sh` |
| **a duplicate main worktree blocked a deploy** | `runtime-worktree.txt` pointed at the node's own worktree, "so a deploy would have built a tree missing the whole batch and the guard would have refused it". Git refuses the second one outright, measured on avell, 18/11: `git worktree add ../two main` -> `fatal: 'main' is already used by worktree at '/tmp/wtprobe/one'`. | `docs/FACTORY.md`; `scripts/test-runtime-binding-preflight.mjs` ("exactly one canonical main checkout is required") |
| **GLIBC 2.39 on mail** | The `mail` node (aarch64, glibc 2.35) was down two days: the installed `14963b6f` binary needs `GLIBC_2.39` and the sentinel retried 424 times. `fleet-install.sh` records the same shape on two hosts (glibc 2.31 and 2.35), both dead on restart - and the node *is* the channel you would fix it through. | `release-glibc` brief; `scripts/fleet-install.sh:12` |

Two more the loop counts rather than fears: `provider_stalled` (a launch that never answered) and
`guard_repeated_calls` are `run_failed` lines in `out.log`; `status` reports them, it does not retry them.

## Stage by stage, with the command

### 1. Brief

    $EDITOR ~/Work/missions/<name>/brief.md      # the artifact, its scope, the evidence that settles it

A brief says what the artifact is and what proves it. It does not say where the worktree is: `stage` adds
that, because a session left to find its own worktree allocated one and looped (item 2 of the table).

### 2. Stage

    scripts/mission.sh stage <name> origin/main ~/Work/missions/<name>/brief.md

Writes the table above: `env`, `prompt.md`, `run.sh`, and a worktree on `change/<name>` cut from the base
commit it resolved (a `git fetch origin main` runs first, and a fetch that fails is not fatal). It refuses,
by name: a name with `/`, `..` or a space; a base that does not resolve; a branch `change/<name>` that
already exists; a worktree that already exists; a missing or empty brief; no `wa` on `PATH`; and a node that
is not the one that staged it. One branch per mission is what keeps `main` out of a second worktree - the
deploy's own preflight requires exactly one canonical main checkout.

### 3. Launch

    scripts/mission.sh start <name>

One fresh session: `wa chat --once "$(cat prompt.md)"`, detached with `setsid nohup`, running in `$M` (the
mission dir, never the repo). `run.sh` exports, before it launches anything:

    export WASM_AGENT_RAW_CODE=codemode
    export RUSTUP_HOME="$TOOLCHAIN/rustup" CARGO_HOME="$TOOLCHAIN/cargo"
    export PATH="$TOOLCHAIN/cargo/bin:$PATH"
    export CARGO_TARGET_DIR="$TARGET"     # ~/wasm-agent/target/m-<name>, this mission's own

`start` refuses while a launch is alive (the pid in `run.pid`, `kill -0`, and `/proc/<pid>/cwd` equal to the
mission dir - a reused pid is not a launch). It never resumes: there is no `--resume` in the runner, so a
launch refused by a held lock is reported and left there. `done` is removed before the launch and written
after it with the rc, so a launch that died is distinguishable from one that finished.

### 4. Watch

    scripts/mission.sh status <name>      # one mission; no name: every mission under ~/Work/missions
    scripts/mission.sh report <name>      # status + failures + verify + REPORT.md + err.log + resume line

`status` reads the files, not the transcript: commits and changed files against the recorded `BASE_SHA`
(`git rev-list --count`, `git diff --name-only`), dirty paths, the live launch, `done`, the last session id,
and `failures` = `grep -c '^! run_failed' out.log`, with the newest failure quoted. A real failure is a
`run_failed` line from `lua/core/run_failure.lua`; the word "failed" in prose is not one.

    wa watch <node> <session>             # a session on another node, read-only
    wa steer <session> "<note>"           # queue a note into a run that is still in flight

### 5. Verify, in the mission's own environment

    scripts/mission.sh verify <name> bash scripts/fast.sh
    scripts/mission.sh verify <name> bash scripts/test-mission.sh

Runs the command in `wt/` with codemode, the toolchain and the mission's `CARGO_TARGET_DIR`; appends
`--- verify <utc> <command> (cwd ...)`, the output and `rc=<n>` to `verify.log`; exits with the command's rc.
It refuses while a launch is alive, so a verify never competes with a session for the same tree.

### 6. Independent review

    wa eval reviewer change/<name> --brief ~/Work/missions/<name>/brief.md
    wa eval report

A reviewer that shares nothing with the session - its own home, its own session (`docs/HARNESS-EVALUATOR.md`).
Self-review is allowed and must be labelled self-review, never independent review, and never a fabricated
receipt. A finding accepted or rejected is marked: `wa eval reviewer mark <id>#<n> accepted`.

### 7. Fix round

    $EDITOR ~/Work/missions/<name>/note.md     # what the review found, as findings, not prose
    scripts/mission.sh start <name>            # a NEW session; out.log keeps the previous one

Start with the blockers. The round is a new session on the same worktree and branch - not a resume - so
nothing inherits the previous turn's context, and a failed launch is never replayed. For a staged mission
the note is appended to the prompt the next time it is staged.

### 8. Integrate

    node scripts/landing-queue.mjs preflight --branch change/<name> --checks "bash scripts/fast.sh"
    node scripts/landing-queue.mjs land --branch change/<name> --checks "bash scripts/fast.sh"

The queue takes the merge tree in order: it refuses a dirty canonical tree nobody owns, retests only what
the move changed, and judges the result against what `main` already fails. `bash scripts/fast.sh` must pass
before you integrate, and the report says what it skipped.

### 9. Land

The same `land` step pushes and reads `origin/main` back; the branch is deleted and the canonical tree is
left clean. Never by hand in the canonical checkout. Then:

    scripts/mission.sh clean <name>            # worktree goes; branch, logs, done, verify.log stay

`clean` refuses a dirty worktree (commit it, or `clean --force` to discard), refuses while a launch is alive,
removes only the worktree and the runner, prunes, and keeps the branch - its commits are the mission's
result. `status` for a cleaned mission still reads `out.log`, `done` and `verify.log`.

### 10. Deploy canary, then the fleet

    wa update --all                                    # read-only: what an update would install, per node
    wa update <canary> --status                        # what the canary runs now
    wa land --ready --canary <node> --account <node>   # waves: canary alone, middle, account node last

A deploy goes canary first and alone, so a broken commit breaks one node. A node that is the channel you
would repair it through (`mail`, `openclaw`) goes last. `scripts/fleet-install.sh <artifact-url>` refuses a
binary whose maximum `GLIBC_` symbol the host does not have, before it swaps anything - that refusal is why
`mail` no longer disappears for two days.

## What the script does not do

No daemon, no watcher, no scheduler: nothing runs between your commands. It does not merge, push, deploy,
review or decide; it does not retry a launch; it does not `pkill` anything. The judgement in steps 6-10 stays
with the operator and the session, and the script's job is to make a mission's state readable without
reading a transcript.
